## ADR-001 · 为什么用 DeepSeek 做主模型、硅基流动做向量化

### 背景

RAG 需要两种能力：**对话生成** 和 **文本向量化**。

### 决策

| 能力 | 选型 | 理由 |
|---|---|---|
| 对话生成 | **DeepSeek `deepseek-chat`** | 国内直连稳定、中文表达自然、价格低（约 1 元/百万 token）、支持流式 |
| 文本向量化 | **硅基流动 `BAAI/bge-m3`** | DeepSeek 官方**不提供 embedding 接口**，必须另找；bge-m3 中文语义能力强、价格极低 |
| 视觉理解 | **硅基流动 `Qwen/Qwen3-VL-32B-Instruct`** | 同上，DeepSeek 不支持图片输入 |

### 关键事实

**DeepSeek 目前只提供文本模型**，没有：

- ❌ embedding / 向量化接口
- ❌ 视觉 / 多模态接口

所以"全用 DeepSeek 一家"在技术上做不到。**多模型搭配是这类应用的正常架构**，不是妥协。

### 代价

需要维护两个 API Key，两个账户都可能出现余额问题（**这是实际踩过的坑**，见 ADR-004）。

## ADR-002 · 多模态功能的方案迭代（三次）

这是项目中最重要的一次技术决策，经历了三轮。

### 第一版：直接识别流派

**设计**：上传年画 → 视觉模型直接判断"属于哪个流派"。

**实测方法**：收集 5 个流派的年画各 1 张，用文件名标注真值，让模型判断。

**实测结果：准确率 20%（1/5）**

| 图片（真值） | 模型判断 | 结果 |
|---|---|---|
| 佛山-神像 | 杨家埠 | ❌ |
| 朱仙镇-门神 | 杨家埠 | ❌ |
| 杨家埠-财神 | 杨家埠 | ✅ |
| 杨柳青-门神 | 杨家埠 | ❌ |
| 桃花坞-戏曲故事 | 杨柳青 | ❌ |

**失败原因分析**：

模型的行为规律非常明显——**凡"色彩浓烈"的都猜杨家埠，凡"雅致细腻"的猜杨柳青**。

它只在按**色彩饱和度**做二分归类，并没有真正区分流派特征（半印半绘 vs 纯套色、线条粗细、题材体系）。

更糟的是：**每次都标注"置信度：高"、"把握较大"** —— 模型在该说"不确定"的时候选择了自信地答错。

**结论**：这条路走不通，且"自信地错"比"承认不确定"危害更大。

### 第二版：视觉描述 → 文本检索

**设计**：不让模型判断流派，只让它描述画面特征；再用描述文本做向量检索，找相似的馆藏档案。

**实测结果：Top1 命中 20%，Top3 命中 40%**

比第一版好，但仍偏低。而且检索top1经常是"佛山"——因为描述里出现的"红、浓烈、满构图"等词，在向量空间中更接近佛山档案。

**问题所在**：向量检索只看文本语义相似度，不判断流派归属。这是检索机制本身的局限。

### 第三版（最终采用）：描述 + 检索 + 讲解三段式

**设计**：

```
① 视觉模型「只描述不判断」
   输出：色彩 / 线条 / 技法痕迹 / 题材 / 构图
   （描述是模型的强项，实测准确可靠）

② 用描述文本做向量检索
   拿到 Top3 相似馆藏，作为「参考资料」而非「答案」

③ 文本模型基于「画面描述 + 馆藏资料」写讲解
   流派表述强制使用「可能是……也可能是……」
   并且必须说明依据、必须给免责提示
```

**实测效果**（桃花坞戏曲故事图）：

```
检索：佛山 60% / 桃花坞 59% / 杨柳青 59%   ← 真值在 Top3 内

讲解：
【这幅画的是什么】画面描绘五位女性与孩童相处的场景：一人怀抱小狗，
                一人弹奏琵琶……（准确描述）
【寓意】这类"仕女娃娃"题材……馆藏未收录这幅画题跋的确切寓意，
       需结合原画文字进一步确认。（诚实说明边界）
【可能属于的流派】可能是杨柳青木版年画，也可能是桃花坞木版年画。
                依据：平涂为主、局部有晕染过渡，符合"半印半绘"……
                佛山年画以大红底描金为特色，与本画色调差异较大，
                可能性相对较低。（给出依据 + 排除理由）
【温馨提示】准确鉴定还需专业机构结合实物与文献判断。
```

**注意一个亮点**：虽然佛山在向量相似度上排第一，但文本模型在融合分析后判断"佛山可能性较低"——**这体现了"检索结果需要模型二次判断"的价值**。

### 为什么最终采用第三版

| 维度 | 直接识别流派 | 三段式融合 |
|---|---|---|
| 准确性 | 20%，且自信地错 | 不给绝对结论，只给候选+依据 |
| 出错时的表现 | 错误的断言 | 仍是"有信息量的专业内容" |
| 契合评分点 | — | 命中「AI 安全与可控性 4%」 |
| 产品定位 | 鉴定工具（做不到） | 讲解助手（做得到） |

**核心洞察**：与其做一个做不到的「鉴定器」，不如做一个做不到也不丢分的「讲解员」。

**这条经验已写进代码注释**（`lib/vision.ts` 顶部），避免后来者重走弯路。

## ADR-003 · 数据读取方式：从 fs 改为静态 import

### 问题

最初 API 路由用这种方式读向量库：

```ts
fs.readFileSync(path.join(process.cwd(), "data", "vectors.json"))
```

**本地运行完全正常，但部署到 Vercel 后会报 `ENOENT`。**

### 原因

Vercel 的服务端函数（Serverless Function）**只打包被静态分析识别到的文件**。

用 `fs.readFileSync` 动态拼路径，打包工具无法静态确定要读哪个文件，于是 `data/` 目录不会被包含进函数包。

### 解决

改为静态导入：

```ts
import rawVectors from "@/data/vectors.json";

export function loadStore(): VectorItem[] {
  return rawVectors as unknown as VectorItem[];
}
```

静态 import 会被打包器内联进产物，保证部署后可用。

### 验证方法

构建后在产物中搜索数据特征串：

```
在 .next/server/chunks/...js（266.9 KB）中找到「杨柳青木版年画」
→ 证明数据确实被打进服务端包
```

## ADR-004 · 线上"配置正常但无法使用"的问题

### 现象

访问 `/api/health` 返回 `ok: true`，两个 Key 都显示"已配置"，但实际问答全部 500 报错。

### 原因

初版健康检查**只判断环境变量是否存在**，不验证其有效性：

- Key 存在但余额为 0 → 显示"已配置" → 实际调用返回 402
- Key 存在但已失效 → 显示"已配置" → 实际返回 401

### 解决

新增深度检查模式：

```
GET /api/health          只查配置存在（不产生费用）
GET /api/health?deep=1   真实调用两端接口，验证有效性与余额
```

深度模式会真的发一次最小请求，因此能发现：

- `402` → 明确提示"余额不足，请到 xxx 充值"
- `401` → 明确提示"Key 无效"
- 网络错误 → 提示检查代理

### 经验

**"配置存在"和"配置可用"是两件事。** 健康检查必须区分这两个层次，

否则会出现"监控全绿但服务全挂"的情况。

## ADR-005 · 图片上传的压缩策略

### 问题

- 手机拍摄的原图通常 3–8 MB
- Vercel 请求体上限约 **4.5 MB**
- 图片 token 消耗与像素量正相关，**原图成本是压缩图的 8 倍以上**

### 解决

**在浏览器端压缩后再上传**（`app/UploadPanel.tsx`）：

```ts
// 最长边压到 1024px，JPEG 质量 0.82
const scale = Math.min(1, 1024 / Math.max(bitmap.width, bitmap.height));
canvas.toDataURL("image/jpeg", 0.82);
```

**实测效果**：

| 图片 | 原始 | 压缩后 | 体积比 |
|---|---|---|---|
| 杨柳青-门神.png | 875 KB (800×649) | 102 KB (768×623) | **8.6 : 1** |
| 桃花坞-戏曲故事.jpg | 109 KB | 117 KB (624×933) | 基本持平（原本已较小） |

### 为什么在浏览器端压缩

- 不占用服务端算力
- 减少上传流量（对移动网络友好）
- 避免超过 Vercel 请求体限制

## ADR-006 · Rerank：为什么检索完还要模型再判断一次

### 观察

在 ADR-002 的实测中，**向量相似度第一名的经常是错误答案**（例如桃花坞的图，佛山排第一）。

### 原因

向量检索衡量的是"文本语义相近程度"，而不是"是否属于同一流派"。

描述里的"红、浓烈、满构图"这些词，和佛山档案的文字天然接近——**但流派的本质差异在技法，不在形容词**。

### 应对

把检索结果定位为**「参考资料」而不是「答案」**：

```
检索 → Top3 候选（可能不准）
     ↓
文本模型结合画面描述做二次判断
     ↓
输出「可能是 A，也可能是 B，依据是……；C 可能性较低，因为……」
```

实测中文本模型确实纠正了检索的排序错误（把佛山排除，保留桃花坞），

**这说明"检索 + 模型判断"的组合优于任何单一步骤。**

## ADR-007 · 为什么把「看图讲年画」拆成两个接口

### 现象

一次性完成「看图 + 检索 + 生成讲解」的 `/api/interpret` 接口，

在 Vercel 上实测耗时 **57.6 秒**，而 Vercel 免费版单次函数执行上限是 **60 秒**。

**只差 2.4 秒就会超时**，在真实网络波动下必然失败。

### 排查过程

先怀疑是提示词太长或 max_tokens 太大，于是用三种配置直接测视觉模型：

| 配置 | 耗时 | 输出 |
|---|---|---|
| 短提示 + 450 tokens | 10.9 s | 250 字 |
| 长提示 + 700 tokens | 9.3 s | 296 字 |
| 长提示 + 450 tokens | 12.9 s | 337 字 |

**直接调用只要 9–13 秒**，说明提示词不是瓶颈。

### 真正原因

耗时由三段串行组成：

```
视觉描述（10–13 s） + 向量检索（1 s） + 讲解生成（20–40 s）
                                        ↑ 生成长文本最慢
```

单次请求把三段串起来，总时长必然逼近上限。

另外，对比不同视觉模型发现：

| 模型 | 耗时 | 质量 |
|---|---|---|
| Qwen3-VL-8B | **5.1 s** | 对本场景足够 |
| Qwen3-VL-32B | 13.3 s | 更细致 |
| Qwen3-VL-30B-A3B | 32.7 s | 最慢 |

### 解决

**① 拆分接口**

| 接口 | 职责 | 实测耗时 |
|---|---|---|
| `POST /api/describe` | 看图 + 检索馆藏 | **12.6 s** |
| `POST /api/compose` | 生成讲解（流式） | **5.5 s** |

每个接口都远离 60 秒上限，安全裕度充足。

**② 视觉模型改用 8B**

描述任务只需客观陈述色彩、线条、题材、构图，不需要复杂推理，8B 足够；32B 保留为可选项（`VISION_MODEL` 环境变量切换）。

**③ 讲解改为流式输出**

前端可以先展示"看到了什么 + 相近馆藏"，再逐字显示讲解，感知等待时间大幅缩短。

### 收益

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 单次总耗时 | 57.6 s（险超时） | 18.1 s |
| 超时风险 | 高 | 低 |
| 首屏反馈 | 等全部完成 | 12 秒先看到馆藏 |

## ADR-008 · 流派判断：从「向量检索」改为「大模型对照鉴别要点」

### 背景

ADR-002 确定了「描述 → 检索 → 讲解」三段式，其中第二步用向量检索找相似档案。

### 实测问题

用 5 张图跑系统性评测，结果很不理想：

| 指标 | 结果 |
|---|---|
| Top1 命中 | **0 / 5（0%）** |
| Top3 命中 | 3 / 5（60%） |

更明显的问题是**系统性偏差**：佛山在 5 次里有 4 次被排到第 1 名。而且所有相似度都挤在 **60%–65%** 之间，区分度极低。

**根因**：向量相似度衡量的是「字面语义接近程度」。描述里的"色彩浓烈""满构图"这类词，和佛山档案的文字天然接近——但流派的本质差异在**技法**（半印半绘 vs 纯套色），这属于需要推理的语义关系，字面相似度抓不住。

### 决策

**放弃用向量检索做流派排序**，改为：

1. 把七个流派的「画面鉴别要点」写成结构化文本（`lib/schools.ts`）
   —— 只写能从画面上看出来的特征，不写历史沿革、传承人名录等不可见信息
2. 把「画面描述 + 七流派要点」一起交给 DeepSeek，用 JSON 模式输出排序、置信度、理由和排除项
3. 向量检索仅保留在问答链路（`/api/chat`）里，用于检索档案正文

### 接口变化

| 原 | 现 |
|---|---|
| `/api/describe` → 描述 + 向量Top3 | `/api/describe` → 仅描述 |
| （无） | `/api/judge` → 对照判断，输出候选+置信度+理由+排除项 |
| `/api/compose`（用相似度） | `/api/compose`（用判断理由） |

### 实测对比

同一张图（桃花坞·仕女抚琴）：

**改为大模型判断后：**

```
桃花坞  把握高  纯套色印刷无手绘，线条工整流畅，色彩清丽，有竖排题字，符合桃花坞要点
武强    把握低  纯套色和满构图与武强吻合，但题材为仕女抚琴，非农事生活，且色彩偏粉紫，不够典型
杨家埠  把握低  纯套色和满构图符合，但色彩非极浓烈撞色，线条非粗犷，题材非门神吉祥娃娃
已排除：杨柳青、绵竹、佛山
```

**关键差别**：向量检索只会给出一个分数，无法解释；大模型能指出「题材为仕女抚琴，非农事生活」这种**可核查的矛盾点**。

### 附带收获

拆成三步后总耗时从 18 秒降到 **10.1 秒**：

| 步骤 | 耗时 |
|---|---|
| describe | 5.1 s |
| judge | 2.1 s |
| compose | 2.9 s |

因为 judge 只输出 JSON（几十字），比生成长篇讲解快得多。

### 另一个重要发现：鉴别要点必须写"可见特征"

最初写要点时混入了历史沿革（如"兴起于明代"），这会干扰判断——模型可能因为描述里没提年代就否定某个流派。

改为**只写画面可见特征**（技法、色彩、线条、题材、观感）后，判断质量明显提升。

## ADR-009 · 关于评测数据集的一个重要教训

### 现象

调试过程中一直觉得"准确率低"，于是回头逐张核查测试图片的标注。

### 发现

5 张测试图里有 **2 张标注可疑**：

| 图片 | 实际观感 | 问题 |
|---|---|---|
| 佛山-神像 | 八仙庆寿题材，米白底、无描金、人物面部有手绘晕染 | 佛山标志是「大红底+描金」，这张完全没有 → 大概率为误标 |
| 朱仙镇-门神 | 绿橙黄撞色极鲜艳、题"老店""曹家" | 朱仙镇应为"厚重偏暗"，这张比杨家埠还艳；"曹家"是杨家埠名号 → 存疑 |

### 教训

**评测集本身不可靠时，所有准确率数字都没有意义。**

之前得到的 20% / 40% / 60% 等指标，都是拿可能错误的答案去比对模型输出，属于无效测量。

### 改进要求

测试图片必须**能明确说出出处**，例如：

> "杨柳青木版年画《连年有余》，天津杨柳青木版年画博物馆藏"

可用来源：中国非物质文化遗产网（ihchina.cn）、各年画博物馆官网、《中国木版年画集成》等学术出版物。

**写不出出处的图，不能用来测准确率。**

### 这也反向验证了产品定位

正因为连一张图的流派归属都存在争议，**「AI 鉴定」这个定位本身就不成立**。

所以产品不做鉴定、只做讲解——这个决策在数据层面再次得到支撑。
