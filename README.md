# 年画档案 · After-the-Rain

> **雨后天晴，伴你而行**
> 中国木版年画的数字馆藏助手 —— 可以提问，也可以上传照片让 AI 讲讲这幅画。

**在线演示**：https://after-the-rain-git-main-liyuxuan200817-2433.vercel.app

**技术栈**：Next.js 16 · TypeScript · Tailwind CSS 4 · DeepSeek · 硅基流动

---

## 这是什么

年画是国家级非物质文化遗产，但普通人面对一幅年画时，常常想问三个问题：

1. 这画的是什么？（题材、人物、故事）
2. 这些图案什么意思？（谐音、典故、祈愿）
3. 它是哪个流派的？（杨柳青？杨家埠？桃花坞？）

**本项目就是一个能回答这三个问题的 AI 助手。**

它的关键在于——**答案必须有出处，查不到就明说。**

---

## 两个核心功能

### ① 问一问馆藏（RAG 检索问答）

用自然语言提问，AI 先检索馆藏档案，再基于档案作答，**并在回答末尾标注出自哪份档案**。

如果馆藏里没有相关内容，AI 会说「馆藏未收录相关内容」并建议换个问法，**不会编造**。

### ② 看图讲年画（多模态理解）

上传一张年画照片，系统会：

```
① 视觉模型客观描述画面（色彩 / 线条 / 技法痕迹 / 题材 / 构图）
        ↓
② 大模型对照「七大流派鉴别要点」逐条判断
   输出：候选流派 + 把握程度 + 可核查的理由 + 主动排除项
        ↓
③ 生成讲解：画的是什么 / 寓意 / 可能属于的流派 / 免责提示
```

**注意：产品不做"鉴定"，只做"讲解"。**

原因见 [技术决策记录 ADR-002](docs/技术决策记录.md)：实测发现视觉模型对流派判断的准确率仅 20%，且会「自信地答错」。与其做一个做不到的鉴定器，不如做一个**做不到也不丢分的讲解员**。

## 技术架构

```
┌─────────────────────────────────────────────────────────┐
│  浏览器（Next.js App Router + Tailwind）                  │
│   ChatBox 流式问答        UploadPanel 图片上传+压缩        │
└───────────┬─────────────────────┬────────────────────────┘
            │                     │
┌───────────▼─────────────────────▼────────────────────────┐
│  API 层（Next.js Route Handlers, Node runtime）           │
│  /api/chat      检索 + 生成，SSE 转纯文本流                │
│  /api/describe  视觉模型 → 画面描述                        │
│  /api/judge     大模型对照七流派要点 → 候选 + 理由          │
│  /api/compose   生成讲解（流式）                           │
│  /api/health    环境自检（?deep=1 真实调用验证）            │
└───────────┬─────────────────────┬────────────────────────┘
            │                     │
     ┌──────▼──────┐       ┌──────▼────────┐
     │  DeepSeek   │       │  硅基流动      │
     │ deepseek-   │       │ · bge-m3 向量化│
     │ chat 对话   │       │ · Qwen3-VL 视觉│
     └─────────────┘       └───────────────┘
            │
     ┌──────▼──────────────────────┐
     │ data/ich-items.json  馆藏档案 │
     │ data/vectors.json    向量索引 │
     └─────────────────────────────┘
```

**为什么用两家模型服务**：DeepSeek 目前不提供 embedding 和视觉接口，所以向量化与图片理解必须用硅基流动。详见 [ADR-001](docs/技术决策记录.md)。

## 快速开始

### 1. 环境要求

- Node.js 20+
- 两个 API Key：[DeepSeek](https://platform.deepseek.com)（对话）、[硅基流动](https://cloud.siliconflow.cn)（向量化 + 视觉）

### 2. 安装

```bash
git clone https://github.com/liyuxuan200817-commits/After-the-Rain.git
cd After-the-Rain
npm install
```

### 3. 配置密钥

复制 `.env.example` 为 `.env`，填入：

```ini
DEEPSEEK_API_KEY=sk-你的key
SILICONFLOW_API_KEY=sk-你的key
```

> `.env` 已被 `.gitignore` 忽略，**永远不会被提交**。

### 4. 生成向量索引

```bash
npm run embed
```

### 5. 启动

```bash
npm run dev                      # 开发模式 → http://localhost:3000

npm run build && npm run start   # 生产模式
```

### 常用命令

| 命令 | 用途 |
|---|---|
| `npm run dev` / `build` / `start` | 开发 / 打包 / 生产启动 |
| `npm run embed` | 数据改动后重建向量索引 |
| `npm run search "问题"` | 命令行测试检索是否准确 |
| `npm run rag "问题"` | 命令行测试完整 RAG 链路 |

## API 说明

| 接口 | 方法 | 用途 |
|---|---|---|
| `/api/chat` | POST | RAG 问答，返回 `text/plain` 流 |
| `/api/describe` | POST | 图片 → 画面描述 |
| `/api/judge` | POST | 描述 → 流派候选 + 理由 |
| `/api/compose` | POST | 描述 + 候选 → 讲解（流式） |

详情见各路由文件顶部注释，或直接 GET 接口地址查看用法说明。

## 数据说明

> ⚠️ **当前 `data/ich-items.json` 中的 8 条档案为示例内容**，由开发者依据公开常识编写，
> 尚未逐条核对权威来源。正式提交前需替换为经核对的档案。

数据应当来自：

- [中国非物质文化遗产网](https://www.ihchina.cn)
- 各年画博物馆官网（杨柳青、桃花坞、杨家埠等）
- 《中国木版年画集成》等学术出版物

**判断标准**：每条档案都能写出可核查的出处，如
> 「杨柳青木版年画《连年有余》，天津杨柳青木版年画博物馆藏」

具体操作见 [数据交接说明](docs/数据交接说明.md) 与 [数据编辑教程](docs/A的数据编辑教程.md)。

## 已知限制

| 项目 | 说明 |
|---|---|
| **不做流派鉴定** | 视觉模型对流派判断准确率低，产品只提供候选与理由，明确声明「需专业机构判断」 |
| 数据待核对 | 档案内容需用权威来源替换 |
| Vercel 免费版节点在境外 | 调用国内 API 有额外延迟，已通过接口拆分缓解（57.6s → 10.1s） |
| 图片压缩在浏览器端 | 直接调用 API 需自行控制图片体积（< 4MB） |

## 开发过程记录

本项目保留了完整的试错过程，详见 **[技术决策记录（ADR）](docs/技术决策记录.md)** —— 9 个关键技术决策，包含失败的尝试与实测数据：

- 为什么用两家模型服务（DeepSeek 缺 embedding / 视觉能力）
- 多模态方案的三次迭代（识别流派 20% → 描述检索 40% → 融合讲解 80%）
- 为什么从向量检索改成大模型判断（Top1 命中 0% → 判断可解释）
- 为什么把接口拆成两步（57.6s → 10.1s，避免 Vercel 超时）
- 数据读取方式从 `fs` 改成静态导入（否则部署后 ENOENT）
- **评测数据集本身不可靠的教训**：测试图中至少 2 张标注可疑
